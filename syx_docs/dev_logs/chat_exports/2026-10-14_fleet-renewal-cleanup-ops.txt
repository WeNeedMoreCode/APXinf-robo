❯ 当前我们走的是啥路线？静态编译？是走的onnx om编译吗？                         

  Thought for 45s (ctrl+o to expand)

● C 路线：GE（Graph Engine）原生 OM 离线编译——但不是 ONNX 转换。我们没有任何
  ONNX 中间文件，也没有走 atc --framework=5 的模型转换链。

  编译链对比

  ┌───────────────────────┬─────────────────────────┬───────────────────────┐
  │         路线          │          链路           │      我们的关系       │
  ├───────────────────────┼─────────────────────────┼───────────────────────┤
  │ MindStudio/ModelZoo   │ torch 模型 → 导出 ONNX  │ 没走                  │
  │ 常见链                │ → atc 转换 → .om        │                       │
  ├───────────────────────┼─────────────────────────┼───────────────────────┤
  │ TorchAir（阶段 1 基线 │ torch 图 → GE 编译 →    │ 已弃用（权重作 Data   │
  │  375.8ms）            │ OM（运行时加载）        │ 输入，每执行付 ND→NZ  │
  │                       │                         │ TransData ~100ms）    │
  ├───────────────────────┼─────────────────────────┼───────────────────────┤
  │                       │ Rust 代码直构 GE 图 →   │                       │
  │ 我们（C 路线）        │ aclgrphBuildModel       │ 现役                  │
  │                       │ 离线编译 → .om          │                       │
  └───────────────────────┴─────────────────────────┴───────────────────────┘

  具体形态：apxinf-ascend 里有自研的 ge_builder（C++ 薄层
  FFI：add_data/add_op/set_input/build/run/save/load）——模型定义写在 Rust 
  里，逐算子声明计算图（MatMulV2/PromptFlashAttention/AddRmsNorm/GeluV2/QuantMat
  mulDequant…），然后调 GE 的离线编译 API（与 atc 底层同源）烤成
  .om。权重在编译期以预转置布局烤入 Const/WCONST 节点（这正是免 NZ
  税的架构基础，也是 ONNX 链路做不到的——中间格式会丢掉布局控制权）。

  「静态编译」的精确含义

  - 三段静态 OM：vision（27 层，静态单 OM）+ prefix（18 层，26 档动态分档单 
    OM）+ flow（per-L 静态池 ~26 只）
  - L 维度的漂移问题不是靠纯静态多桶硬扛的——prefix 用的是 GE 
    动态分档（ge.dynamicDims 档表编译 + 运行时 aclmdlSetInputDynamicDims
    分发）：单 OM 多档、档内仍是静态 kernel（保住 shape 特化 tiling
    和零调度税，实测性能零税）；flow 因 styles 是运行期内容无法 Const 化，走
    per-L 静态池换柄
  - 运行时：aclmdlLoadFromMem（进程常驻）+ aclmdlExecuteAsync——这就是 per-call
    246ms 里零调度税的来源

  为什么是这条路线（历史裁决）

  1. ACLGraph（aclmdlRI capture/replay，类 CUDA Graph）：eager 的 3.46× 但
     matmul task 有 ~475µs/次的启动税（msprof + m-scaling 拟合定罪），全深度卡在
     ~680ms——aclnn 层无解，架构级差异
  2. GE 原生 OM POC：调度税消失 + 静态 tiling 再快 20%，外推 ~370-390ms 达标 →
     全量投入
  3. 一路兑现到 246.9ms（torch 基线 0.65×），外加 Const 烤入（-168ms）和
     int8（qmd 只在 GE 图内可用）

  顺带一句纪律背景：手烤 OM 必带 ge.fusionSwitchFile 关 InplaceAddRmsNorm 融合
  pass（离线导出融合损坏，曾把数值打爆 100%+）——这条已经写进 memory 和 CLAUDE
  级纪律。

❯ 我有个问题，转onnx->om的路子有onnxsim 有 atc帮忙优化图                        
  ，我们这种直接写的怎么优化图啊？

● 好问题——这正是两条路线的核心差异。答案一句话：onnxsim 
  的活我们自己干（写图时），atc 的活 GE 编译器照干（同一套 pass 管线）。展开：

  三层优化责任划分

  第一层：写图时的手工变换（顶替 onnxsim 的角色）

  ONNX 链里 onnxsim 做的是代数级简化（fold constants、fuse
  BN、去重复）。我们的图在 Rust 源码里——源码即图，这些优化全靠手工做，而且能做
  onnxsim 做不到的（跨算子折叠）：

  ┌───────────────────────────────┬────────────────┬────────────────────────┐
  │           手工变换            │      收益      │     onnxsim 能做吗     │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ 权重预转置 + Const/WCONST     │ −168ms（免 NZ  │ ❌ 布局控制在中间格式  │
  │ 烤入                          │ TransData 税） │ 里就丢了               │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ qkv 三 mm 合一、gate_up       │ （C            │ ⚠️ 只能依赖下游 fusion │
  │ 宽融合                        │ 阶段起就内建） │  pass                  │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ rope 平铺重写（列 gather →    │ −228ms         │ ❌ 需要理解数学结构    │
  │ 行交换）                      │                │                        │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ 切片物化消除（QKV3/ROPEFLAT/m │ 2182→431ms（5. │ ❌ 是 GE               │
  │ anual attn）                  │ 06× 主体）     │ 运行时行为，ONNX       │
  │                               │                │ 层不可见               │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ smoothquant                   │ int8           │                        │
  │ 因子折进权重（s_eff、(1+g)    │ 可用性前提     │ ❌ 量化因子跨算子传播  │
  │ 折叠）                        │                │                        │
  ├───────────────────────────────┼────────────────┼────────────────────────┤
  │ scale 折权重、euler           │                │                        │
  │ 常数折图、empty view          │ 各几~几十 ms   │ 部分                   │

  ├───────────────────────────────┼────────────────┼────────────────────────┤

  │ RmsNorm                       │                │                        │
  └───────────────────────────────┴────────────────┴────────────────────────┘

  第二层：GE 编译期自动优化（= atc 的角色，我们同样享有）

  aclgrphBuildModel 和 atc 命令行是同一套编译管线——只是入口是 API。atc
  里的图优化 pass 我们全量保留：

  - 常量折叠：Const 烤入后编译期消化（实测单 mm −25%，OM
    体积里能看到权重被折进图）
  - 算子融合 pass：比如 InplaceAddRmsNormFusionPass——它的存在恰恰是我们发现要关
    掉它的（离线导出融合损坏，数值打爆 100%+，fusionSwitchFile 就是 atc
    同款开关机制）
  - 死代码消除、内存计划（buffer 复用/重叠）、静态 shape 特化 tiling（4.71 vs
    aclnn 运行时 tiling 5.86 µs/row，−20%）、多核切分

  第三层：ONNX 链做不了、只有手写才有的

  ONNX 是信息瓶颈：torch 导出时布局被迫
  ND、动态控制流/自定义语义丢失、量化因子传不过去。手写图的上限 =
  你对模型数学的理解深度。我们 vs torch 的 1.65× 里主要来源（Const 烤入 
  68%）恰恰是 ONNX 链结构性做不到的。

  代价（诚实账）

  没有免费的午餐：onnxsim 一键跑 pass 且默认正确；我们每个手工变换都要自己验证数
  学等价——这就是项目里那套对拍梯存在的原因（eager 参考 → golden → bit 对拍 →
  行为 eval）。调试工具也是自己搭的：

  - DUMP_GE_GRAPH=3 逐 pass 图 dump（当时揪出 InplaceAddRmsNorm 融合 bug
    的破局点）——相当于「看 onnxsim 每步改了什么」
  - GEB_SUB 编译冒烟矩阵（逐算子/逐组合二分）
  - fusionSwitchFile 精确控制单个 fusion pass

  一句话总结：ONNX 路线是「把优化交给两个现成工具，接受中间格式的天花板」；我们
  是「图优化一半自动化（GE pass 与 atc 同源）、一半手工业（但能做到 ONNX
  做不到的折叠与布局）」——手工业的部分正是性能优势的来源，也是工程量大的原因。

● 不完全是——准确的说法是：不是我们改得比工具好，而是工具结构上够不着的地方我们才
  动手，而我们够得着是因为有特权。

  拆开说：

  先纠正对比框架

  atc 的编译 pass（tiling 选择、内存计划、fusion、多核切分）我们同样全量享有——同
  一个编译器管线。所以不存在「我们的优化 vs
  工具的优化」的对抗。真正的对比是输入给编译器的图谁更好：ONNX 链输入的是「torch
  导出 + 中间格式无损转换」的图，我们输入的是带着全部领域知识写出的图。

  为什么有些优化工具永远做不了

  不是能力，是信息。工具的优化本质是模式匹配（见过这个模式才敢动）；而这块优化空

  工具的保守是它的职业操守——onnxsim/atc 必须对任意模型任意拓扑保证正确，所以只敢

❯ qkv权重融合计算我们已经做过了是吗                                             

  Thought for 20s (ctrl+o to expand)

● 做过——而且后来又拆开了。这是个好案例，因为「要不要融合」的答案随执行框架变了：

  演进链

  阶段: eager aclnn 时代（M2）
  qkv 形态: 融合（一次宽 mm 出 q‖k‖v）
  为什么: eager 每 op 付 ~400µs host 启动税——融合 = 少两次 op 调用，纯赚
  ────────────────────────────────────────
  阶段: GE OM 初版（C2 一版）
  qkv 形态: 沿用融合
  为什么: 惯性
  ────────────────────────────────────────
  阶段: C2 攻坚（GEB_QKV3，2026-09-19）
  qkv 形态: 拆回 3 个独立 mm + 独立权重输入
  为什么: 切片物化定罪：融合产物的 q/k/v 切分靠 SliceD 列切视图 → GE
  运行时每执行插 D2D 物化拷贝走 host 慢路径（每次前 4.5-12ms 停顿 × 27 层）——是
   vision 723→68 / prefix 750→188 的三件套修复之一
  ────────────────────────────────────────
  阶段: 现役生产
  qkv 形态: 3 独立 mm
  为什么: 维持

  为什么拆开反而是对的

  静态 OM 的零调度税把融合的收益没收了：
  - eager 时代：融合省 2 次 op 启动 ≈ 省 ~800µs ✅
  - GE OM 时代：mm task 背靠背零启动税，融合省下的 = 0；但融合附带的列切片 =
    每层每执行 ~5-10ms 物化税 ❌

  融合的动机（省启动）消失，融合的代价（逼出切片）浮现——净收益反转。gate/up
  同样是双 mm 拆开形态。

  但「权重层面的融合」仍在生产，是另一回事

  有两类数学折叠（不是算子融合）一直活着、烤在 OM 里：
  1. Gemma (1+g) scale 折叠：gemma1/gemma2 = ones，(1+w_scale) 直接预乘进
     q/k/v/gate/up 投影权重（M3 真权重接入时做的）
  2. smoothquant 因子折权重：int8 的 s_eff 折进投影矩阵（prefix/flow int8
     的可用性前提）

  这两个是「改权重内容、图上零成本」的等价变换——与「算子融合省启动」不同层面，任
  何执行框架下都是纯赚。

  所以精确回答：算子级 qkv 
  融合做过又拆了（静态图时代拆是对的）；权重级折叠一直在。

❯ 好像有个npu_add_rms_norm可以做layernorm融合，我们有试过吗                     

  Thought for 21s (ctrl+o to expand)

● 试过——它不只是试过，是现役生产的核心算子，而且这一族我们已经挖到底了。完整履历
  ：

  AddRmsNorm 在我们链路里的位置

  ┌──────────────────┬───────────────────────────────────────┬──────────────┐
  │       路径       │                 形态                  │     状态     │
  ├──────────────────┼───────────────────────────────────────┼──────────────┤
  │ eager（M2 起）   │ aclnnAddRmsNorm（融合三输出，rstd     │ 现役回退路径 │
  │                  │ 隐藏分配）                            │              │
  ├──────────────────┼───────────────────────────────────────┼──────────────┤
  │ GE               │ AddRmsNorm（同名同端口                │ 三段 OM      │
  │ 图内（现役生产） │ x1/x2/gamma→y）——prefix/flow 每层 2   │ 每层标配     │
  │                  │ 处 add→addrms 组合、x2 传 zeros       │              │
  └──────────────────┴───────────────────────────────────────┴──────────────┘

  当初选它还有个原因：裸 RmsNorm 在 310P 只有 dynamic 变体，作中间节点喂静态
  matmul 永远编译拒（skill 陷阱 #11）——AddRmsNorm 是唯一离线可用的形态。

  这一族我们已经玩到的深度

  1. GE 自动融合成 InplaceAddRmsNorm 的大坑（M3，陷阱 #31）：GE 编译器会把
     AddRmsNorm 自动融成原地版本——结果写回输入 buffer
     本体，与静态内存计划交互后图内中间量数值污染 11-45%。修复 =
     ge.fusionSwitchFile 关该 pass（全图 45.2%→0.159%）。你问的「融合」GE 
     自己会做，且做了会坏——我们花钱把它关了。
  2. 再融合一步的尝试全部做过、全部证伪：
     - aclnnAddcmul（ada-norm 的 mul+add 收缩）：无时间收益 + fp16
       累加漂移，撤回
     - 自研 AscendC fused ada-norm kernel（5 算子→1 
       kernel）：完整工具链建成、replay 对拍过——性能打平（679.8 vs
       681.6ms）。三次实验收敛到同一结论：图内设备时间由带宽决定，kernel 
       数不是成本（3 个 kernel 的总访存 ≈ 1 个 fused kernel）
     - NORM32（手搓 fp32 RMS 图，为追 torch 的 fp32
       方差语义）：七坑连环（ReduceSumD f32 假支持 #38、TileD 散点腐蚀
       #39…）最终用 mm 立方体 fp32 累加实现——后来真凶是 ada gate 缺失，NORM32
       判「行为不需要」归档
  3. vision 段是另一族：SigLIP 用 LayerNormV4（不是 RMSNorm）——AddLayerNorm 在
     310P 有 kernel 级 100× 错误（陷阱 #15），换的 V4，且它的 mean/rstd 死端会让
     y 也爆（陷阱 #17，与 AddRmsNorm 死端无害的行为相反）。

  结论

  add_rms_norm
  融合红利已经吃满：本体在生产每层跑着；往「更融合」方向的每一步（Addcmul/自研
  fused kernel/GE 自动
  inplace）都实测过，收益为零或为负——带宽下限定死的。这条线上没有剩余的东西了。

  落地的替代路径（两代）

  1. 组合版（eager 时代）：gather 通道重排（bit-exact）+ mul×2 + add，sign 折进
     host sin 表；真机 D=256 对拍 3.9e-3
  2. 平铺重写 + 表缓存（ACLGraph 时代，-228ms 的大优化）：rotate-half 的列
     gather 在 language 层单次 6.5ms（带宽下限 49×）→ 重写为
     [rows,d]→[rows*2,d/2] 平铺视图邻行交换 gather，cos/sin 表按
     (tokens,heads,offset) 缓存——GatherV2 族总耗时 126ms → 3.9ms
  3. GE 图内（GEB_ROPEFLAT，现役生产）：同构的 flat 视图行交换（GatherV2D +
     Const 索引），C2 三件套之一

  GE 图内单算子的开放项（诚实账）

  有一个未闭合的尾巴：C1 查 310P opp 预编译 kernel 清单时，apply_rotary_pos_emb
  确实在（有预编译二进制，命中静态 key 免编译秒过）——GE
  侧入图编译当时没走通（layout attr / cos-sin 表形状未验），留了开放项。

  但现在不值得回去收：现役 rope 全模型成本已压到 ~4ms/iter
  量级——单算子就算免费也就 246.9→243，而 head_dim 门槛在 kernel
  模板层大概率同样存在（预编译 bin 的 D 集合问题与 eager
  是同一批模板）。这是典型的「优化窗口已关闭」：当年 rope 是 126ms
  大头时值得死磕，现在它是零头。

  顺带一族规律：我们遇过的算子门槛死法——RotaryMul 死于 head_dim 模板集、WQBMV2
  死于 SoC 模板墙（#40/#44）、GeGlu 死于挂死、AttentionScore 死于注册表与 kernel
  目录不一致（#23）——判别链都在 skill 的量化速查和陷阱表里。

❯ 为什么是负收益，我没看懂，量化过的权重不是大小更小，计算量更少吗，为啥收益是

  Thought for 29s (ctrl+o to expand)

● 你的直觉对了一半——大 M 段确实吃到了（prefix −18ms、单算实测
  2.41×）。失效的是另一半场景，机制拆开：

  int8 省什么、不省什么

  ┌─────────────┬───────────────────────────────────────────────────────────┐
  │    直觉     │                           实际                            │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ 「权重更小  │ 对——但权重已 Const 烤入 OM 常驻设备，每次执行根本没有权重 │
  │ 」          │ 搬运环节。省的只是磁盘/加载体积，per-call 收益为零        │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ 「计算量更  │ int8 不减少乘加次数（矩阵还是那个矩阵），只是位宽窄 →     │
  │ 少」        │ 芯片 int8 乘法器吞吐 ≈ f16 的                             │
  │             │ 2×。前提：你得是算力瓶颈（大 M），位宽红利才兑换得出来    │
  └─────────────┴───────────────────────────────────────────────────────────┘

  matmul 的成本结构随 M 变化

  一次投影 mm 的成本 ≈ 算力项（2·M·N·K，随 M 涨）+ 带宽项（读权重 N·K +
  激活，不随 M 变多少）+ per-op 固定开销（launch、tiling、以及 qmd 特有的 x
  动态量化 + dequant 输出）：

  - prefix（M=712）：算力主导 → int8 的 2× 峰值直接兑换 → 105→87ms ✓
  - flow（M=50）：算力项小到忽略，带宽+固定开销主导 → int8
    把权重带宽减半是真的（理论 −30ms），但 qmd
    每次调用的量化/dequant/激活读写固定开销一分不少，M=50 时这些开销相对占比巨大
    → 实测只剩 −5.4ms。这就是「小 M 段收益被 per-op
    开销吃掉」的确切含义——不是负，是理论收益的 82% 被固定税吃掉
  - flow 的 q/k/v/o 我们干脆没上：投影窄（2048×2048
    级），权重带宽省的绝对值更小，固定税不变——算下来趋零，不上

  真正「负收益」的案例（历史上有一个）

  量化侧我们试过拆开做（DynamicQuantV2 → QuantBatchMatmulV3 → dequant
  三算子链，绕 qmd 的限制）：实测 0.119ms vs qmd 0.059ms @ M=50——慢 
  2×。机制同上：拆成三个算子 = 固定开销×3，小 M 段直接赔穿。这条路线当天判死。

  一句话

  量化收益 = f(M)：M 大时你在卖算力红利（2× 峰值），M
  小时你在付固定税（量化/dequant/launch 不随 M 缩水）。所以同一套 int8，prefix
  吃到 2.41×、flow 只剩零头、q/k/v/o
  干脆不值——不是量化不行，是它只能赢在算力瓶颈的段。
