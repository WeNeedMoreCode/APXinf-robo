● 好问题——口径不对齐，这正是我说“真稳态数字要专门 bench”的原因。拆开看：

  378ms 基线的口径

  阶段 1 的 bench（bench_npu.json）有两个数：
  - model_ms P50 = 376.4ms ← 平时说的 378 基线就是这个
  - total_ms P50 = 383.8ms（外围 glue：噪声生成、图像预处理、动作后处理）

  关键是 torch 路径里我说的那些 host 计算——styles（time_mlp）、euler 步进、mask 
  构造——全都跑在 torch 的 forward 内部，所以它们算在 376ms 里面。torch
  的“模型侧”是含全部模型内 host 工作的全口径。

  我们 247.7ms 的口径

  只算了三段 OM 的设备执行：
  - vision 56.11 + prefix 115.99 + flow 7.57×10
  - 不含：每步 styles 的 host 计算 + h2d 换绑、pk/pv 的 host 中转（prefix 出 →
    host → flow 进）、x0 构建(token 查表/拼接)、噪声生成

  而这些项在 torch 基线里都在 forward 内算着呢。所以：

  247.7ms vs 376ms 现在是"我们的设备时间 vs 
  他们的全模型时间”——比较对我们是偏乐观的。

  实际差距多大

  bring-up 计时给了个上界：flow 段 10 步 2.17s（含每步 host styles + 换绑）≈
  217ms/步 vs OM 执行 7.6ms/步——host glue 目前比设备计算重一个数量级（bring-up
  口径还混着 BISECT 对拍开销，真值要低些，但量级如此）。也就是说当前形态下 e2e
  单次调用可能远不止 248ms，host 侧反而是新瓶颈。

  好消息是这些 host 开销都有明确的压缩路径，而且 torch
  基线证明它们压完后可以只占 ~8ms 量级（total−model 差）：
  1. styles 预计算批处理——10 步的 styles 一次性算好（时间步固定），不是每步现算
  2. pk/pv 设备直连——已在 M3 后置清单
  3. x0/euler 图内化或一次构建

  所以诚实的说法是：设备侧 0.66× 已坐实（这是 C 
  路线零调度税论点的验证），全模型口径待 host glue 压完才能真正对线 
  378ms。这也是为什么 M3 剩余清单里“真实 e2e 稳态 bench”要排在 LIBERO
  前面——先拿到干净的全口径数字再谈对标。
