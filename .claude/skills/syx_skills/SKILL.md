# Skill 创建器

一个用于创建新 skill 并迭代改进它们的 skill。

概括来说，创建 skill 的过程如下：

- 决定你想要这个 skill 做什么，以及大致怎么做
- 写一份 skill 的草稿
- 根据需要验证和迭代：可以跑测试 prompt，也可以直接让用户试
- 重复直到满意

你使用这个 skill 时的任务是弄清用户处于这个过程的哪个阶段，然后帮助他们推进。比如，用户可能说"我想做一个做 X 的 skill"。你可以帮助缩小他们想要的范围，写草稿，写测试用例，确定他们想怎么评估，运行所有 prompt，然后重复。

另一方面，用户可能已经有了一份 skill 草稿。这种情况下可以直接进入评估/迭代循环。

当然，你应该始终保持灵活，如果用户说"我不需要跑一堆评估，随意聊聊就行"，那也可以。

然后，在 skill 完成后（但顺序同样灵活），你还可以运行 skill description 优化器，我们有一个专门的脚本用于优化触发效果。详见 [测试与评估](references/testing_and_evaluation.md)。

## 泛化优先（核心原则）

创建 skill 时，默认产出**泛化型 skill**，而非绑定到特定项目的专用 skill。

**泛化型**：抽象到其他场景可以复用。例如"调试方法论"、"Web 应用搭建"、"数据迁移检查清单"。另一个 session、另一个项目、另一个用户拿起这个 skill 就能用。

**专用型**：绑定到特定项目、特定模型、特定算子。例如"Ball Query 算子开发指南"、"XX 购物网站搭建"。

**为什么默认泛化**：skill 的价值在于复用。如果 SKILL.md 里塞满了 "Ball Query 如何如何"、"Group Points 如何如何"，其他 session 看不懂这些上下文，这个 skill 对它们就没有意义。你在写 skill 时脑海中有当前项目的全部上下文，但使用这个 skill 的其他 session 没有。

**具体做法**：

- **SKILL.md 只放抽象的方法论和模式**。不放特定项目的名称、特定算子的行为、特定模型的参数。如果发现自己在写 "当 XXX 算子YYY 时"，停下来，把 XXX-YYY 的具体细节移到 reference 文件，SKILL.md 只写通用模式的要点加一个指向 reference 的链接。
- **具体案例放 reference 文件**。SKILL.md 中路由到它们："以 Ball Query 算子为例的完整开发记录见 `references/ball_query_example.md`"。
- **泛化 skill 的引用必须自包含**：引用的文件放在 skill 目录内，案例用快照（接受与源文档漂移、手动同步）。指向仓内其他路径的指针看似优雅（"内容以源文档为准"），实际让 skill 寄生在那个仓上——换台机器、换个项目链接即死，通不过上面的自检。专用 skill（用户明确要求的那种）不受此限：它本来就活在该仓里，引用仓内路径没问题。
- **只有用户明确要求时才做专用 skill**。如果用户说"我要一个只针对 XX 项目的 skill"，才可以把特定细节写进 SKILL.md。否则默认产出泛化型。

**自检**：写完 SKILL.md 后，问自己：一个完全不了解当前项目的 session，能直接用这个 skill 吗？如果答案是不能，说明里面塞了太多项目特定的东西。

## 记事实，不记猜测

当 skill 内容来自实测总结时，遵循以下约束：

- **不要把推测写成结论**。如果某个现象的根因没有通过实验验证，记为"推测 X 导致，未验证"，不要写成"X 导致"。读者需要区分"已验证的事实"和"合理的猜测"。
- **不要把未探明可达的路径记为不可达**。某条路径当前没有走通，不代表它一定不可行。可能是实现方式不对、条件不满足、或者尚未尝试足够多的变体。记为"在当前条件下未找到有效路径"而非"不可行"。
- **逻辑合理的确定性推理可以记录**。如果 A 已验证、B 已验证、且 A→B 的因果链是确定性的（非概率推断），那么"A 导致 B"可以作为结论记录。但如果中间存在未验证的环节，必须标注为推测。
- **区分三层信息**：
  1. **事实**：实际观察到的现象、测试的 pass/fail 结果、具体的数值
  2. **推测**：对现象的归因，尚未设计实验验证
  3. **结论**：经过验证的因果关系

这样做的价值：其他 session 读到 skill 时，会根据内容做决策。如果把推测当成结论，后续 session 会基于错误的前提行动。如果把未验证不可达的路径记为不可达，后续 session 会放弃原本可行的方案。

## 记终态，不记过程

skill 是定稿规范，不是达成它的讨论记录。用户纠正过的格式、试过又放弃的方案、规则为什么不是别的样子——这些是会话过程，未来 session 不需要重读一遍已经结束的讨论。

- 只写"怎么做是对的"：格式、约定、判据，直接给终态
- why 可以记，但记的是规则背后的道理（帮未来 session 把规则正确套用到新场景），不是如何走到这里（被否决的方案、对比论证）
- 自检一句话：这句话删掉后，未来 session 还能正确执行吗？能，它就是过程残留

## 创建 skill

### 捕获意图

从理解用户的意图开始。当前对话中可能已经包含了用户想要捕获的工作流（例如，他们说"把这个变成 skill"）。如果是这样，先从对话历史中提取答案——使用的工具、步骤顺序、用户做的修正、观察到的输入/输出格式。用户可能需要填补空白，并应在进入下一步之前确认。

1. 这个 skill 应该让 Claude 能做什么？
2. 这个 skill 应该在什么时候触发？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 是否需要测试？具有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤）受益于定量测试。具有主观输出的 skill（写作风格、艺术）通常更适合定性审查。也有些 skill 完全不需要测试——写完就够用了。根据 skill 类型建议合适的验证方式，但让用户做最终决定。

### 访谈和研究

主动询问关于边界情况、输入/输出格式、示例文件、成功标准和依赖的问题。在弄清这些之后再写测试 prompt。

检查可用的 MCP——如果对研究有用（搜索文档、查找类似 skill、查找最佳实践），通过子 agent 并行研究（如果有子 agent 的话），否则内联研究。准备好上下文以减少用户的负担。

### 评估架构（关键步骤）

**在写 SKILL.md 之前，必须先决定用单文件还是多级路由架构。** 这一步经常被跳过，导致 skill 越写越臃肿，最后才想起来要拆。

判断标准——出现以下任一情况，就读 [references/skill-architecture-patterns.md](references/skill-architecture-patterns.md) 选架构模式：

| 信号 | 说明 |
|------|------|
| 用户描述的工作流有**明确的分叉路径** | 比如"先 A 路径、不行再 B 路径"、"部署用 OM、调试用 torch_npu" |
| 内容天然按**多个独立维度**组织 | 比如"按语言分 Python/TS/Java"、"按框架分 PyTorch/TF" |
| 预计 SKILL.md 会**超过 300 行** | 单文件上限约 500 行，留余量提前分层 |
| 已有的 flat skill **变得越来越难维护** | 改一处牵动多处、用户找不到要读哪段 |

**如果以上都不满足**，用单文件 SKILL.md 就行，不需要读架构模式文件。

**如果任一满足**，读 `references/skill-architecture-patterns.md`，按里面的"如何选择架构"三问决策（内容量、维度数、维度独立性），选 Router-Delegate / 渐进式路由 / 路由+专用组合 中的合适模式。

**为什么这步重要**：架构决策决定了整个目录结构和 SKILL.md 的写法。先选架构再写，比写完再拆省 10 倍力气。cuda-to-npu 就是因为先定了 Router-Delegate 三路径结构，才一次写对。

### 编写 SKILL.md

根据用户访谈，填写以下组件：

- **name**：Skill 标识符
- **description**：何时触发，做什么。这是主要的触发机制——包括 skill 做什么以及在什么上下文中使用它。所有"何时使用"的信息都放在这里，而不是正文中。注意：目前 Claude 有"欠触发"skill 的倾向——在 skill 有用时不去使用它。为了对抗这一点，请让 skill description 稍微"主动"一些。比如，与其写"如何构建一个简单快速的仪表盘来显示 Anthropic 内部数据"，不如写"如何构建一个简单快速的仪表盘来显示 Anthropic 内部数据。每当用户提到仪表盘、数据可视化、内部指标，或想显示任何类型的公司数据时，请确保使用此 skill，即使用户没有明确要求'仪表盘'。"
- **compatibility**：所需工具、依赖（可选，很少需要）
- **skill 的其余内容 :)**

### Skill 编写指南

#### Skill 的结构

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML frontmatter (name, description 必需)
│   └── Markdown 指令
└── 打包资源 (可选)
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载到上下文中的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

Skill 使用三层加载系统：
1. **元数据** (name + description) - 始终在上下文中（约 100 词）
2. **SKILL.md 正文** - 在 skill 触发时在上下文中（理想情况 <500 行）
3. **打包资源** - 按需使用（无限制，脚本可以不加载直接执行）

这些词数是近似值，如果需要可以更长。

**关键模式：**
- 保持 SKILL.md 在 500 行以内；如果接近这个限制，添加一个额外的层次结构，并附带明确的指针，告诉使用该 skill 的模型下一步去哪里查找。
- 从 SKILL.md 中清晰地引用参考文件，并说明何时读取它们
- 对于大型参考文件（>300 行），包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

**大型 Skill 架构**：架构决策已在前面"评估架构"步骤完成。如果选了多级路由模式，SKILL.md 只写路由表和场景检测，具体内容放子目录。详见 [references/skill-architecture-patterns.md](references/skill-architecture-patterns.md)。

#### 编写模式

在指令中优先使用祈使语气。

**定义输出格式** - 你可以这样做：
```markdown
## 报告结构
始终使用以下确切模板：
# [标题]
## 摘要
## 关键发现
## 建议
```

**示例模式** - 包含示例很有用。你可以这样格式化（但如果示例中有"输入"和"输出"，你可能想稍微变通一下）：
```markdown
## 提交消息格式
**示例 1：**
输入：使用 JWT token 添加了用户认证
输出：feat(auth): 实现 JWT 认证
```

### 写作风格

尝试向模型解释事情为什么重要，而不是使用生硬的"必须"。运用心智理论，尝试使 skill 具有通用性而不是过度局限于特定示例。先写一份草稿，然后用新的视角审视并改进。

## 验证和迭代

### 轻量验证（适用于大多数 skill）

写完 skill 草稿后，想出 2-3 个现实的测试 prompt——真实用户会真正说的那种。与用户分享：[你不必使用这个确切的措辞] "这里有几个我想尝试的测试用例。这些看起来对吗，还是你想加更多？" 然后运行它们。

对于不跑定量测试的 skill，直接让用户试用并给反馈就够了。

### 改进 skill

根据用户反馈改进 skill 时：

1. **从反馈中泛化。** 你和用户只在少数几个例子上迭代，但 skill 要能被使用无数次。与其做细碎的过拟合改动，不如拓展思路，使用不同的比喻或推荐不同的工作模式。
2. **保持 prompt 精简。** 删掉没有发挥作用的内容。阅读对话记录——如果 skill 在让模型浪费时间做无用功，删掉导致这种行为的部分。
3. **解释原因。** 努力解释每件事背后的**原因**。如果你发现自己在用全大写字母写"总是"或"从不"，这是一个黄旗——重新表述并解释原因。
4. **寻找跨测试用例的重复工作。** 如果子 agent 都独立编写了类似的辅助脚本，这是一个信号：skill 应该打包该脚本。

持续迭代直到用户满意、反馈全部为空、或你没有在取得有意义的进展。

### 定量测试与评估（可选）

对于需要严格验证的 skill，我们有完整的测试框架：并行运行带/不带 skill 的测试、自动评分、基准聚合、查看器。详见 [测试与评估](references/testing_and_evaluation.md)。

## 打包和呈现（仅在 `present_files` 工具可用时）

检查你是否有 `present_files` 工具的访问权限。如果没有，跳过此步骤。如果有，打包 skill 并向用户呈现 .skill 文件：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包完成后，引导用户到生成的 `.skill` 文件路径，以便他们安装。
