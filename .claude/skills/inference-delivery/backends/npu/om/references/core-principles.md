# 核心设计原则

以下原则贯穿所有 Workflow，每条都解释了"为什么"——理解原因才能在模糊场景中做出正确判断。

## 原则 1：大图优先

优先围绕本次交付场景寻找最大连续 tensor 计算边界，将共享输入、替换点、主要重计算或输出消费者的分支合并为同一候选。若用户未指定场景，优先以官方 README、demo、benchmark 或 service API 中最高频、输入契约稳定且代表主要重计算的入口为基准。原因：每切一次图就多一次 host-device 数据搬运和 context 切换，直接增加推理时延。小图拆分只在大图导出/ATC/验证/接回失败后作为重规划结果出现，且必须先判断能否合并前后子图；不得因为样例入口分散、覆盖入口更多或 wrapper 编写方便而提前拆成多个 OM。

## 原则 2：图侧主策略唯一

每个 OM 只选一种输入形态策略：`static / dymbatch / dymhw / dymdims / dymshape`。选择逻辑：

- 部署契约可固定 batch 和空间/序列尺寸 → `static`（首选，最高推理效率）
- 仅 batch 动态且可分档 → `dymbatch`
- 仅 H/W 空间尺寸动态且可分档 → `dymhw`
- 有限多个维度组合可枚举 → `dymdims`
- 动态已表达为图内 tensor shape ops，且希望减少分档复杂度或无法稳定分档 → `dymshape`

关键判断：若动态性来自 Python 控制面、构造参数或影响图内数学的非 tensor 值，必须先补齐源码契约、语义拆分或 runtime variant，不能用单个样例值替代控制参数建模。只有控制值已被正确建模为图输入、固定部署契约或明确 runtime variant 后，才可选择 `dymshape` 或其他动态策略交付。代码支持可变不等于交付必须可变——先看交付入口、服务契约、预处理、padding、resize、bucket、上游裁剪或候选生成是否已经固定了某些轴。

## 原则 3：输出保真

替换点的原始输出全集必须先记录。本次适配场景内会被下游消费的输出，必须由 OM 真实输出或原始实现提供。不得用零张量、随机张量、常量或仅形状占位替代参与后续计算的真实输出。原因：一个被占位的输出可能在下游引发静默精度劣化，且难以在端到端验证中定位根因。

若某输出不导出或某功能分支本轮不支持，必须记录：全部下游消费者、为何不进入后续计算、是否由 fallback 覆盖、后续风险。

## 原则 4：接回 context 隔离

同进程混用多个 `.om`，或 `.om` 与 `torch_npu` / aclruntime / ais_bench 混合运行时，必须用 runner 模式做 context 隔离。原因：Ascend ACL 的 stream 和 context 是进程级状态，不隔离会导致 OM 推理和原始 runtime 互相踩踏，表现为随机精度异常或 segfault。

多 OM 场景下的隔离协议：每个 `.om` 由独立 OMRunner 实例管理；创建 session 前保存原 runtime context，创建后恢复；每次 infer 前切到 session context，在 `finally` 中恢复；OM 与原始流程之间用明确的 host/tensor 数据契约交接。具体 runner 代码模板由 `ascend-om-pipeline-adapter` 维护。

## 原则 5：候选状态机闭环

每个候选必须沿状态机推进直到闭环：

```text
pending → selected → in_progress → om_done → validated → integrated
                                  ↘ failed_replan / fallback / excluded
```

`fallback` 只能作为尝试失败、重规划不成立、用户确认排除或证明不属于可图化计算面后的最终状态，不得在候选识别阶段用来跳过 OM 尝试。每个候选需记录：所属功能分支、是否主链热点、输入/输出 shape 变化来源、控制参数及来源、推荐图侧策略、当前状态、暂缓原因、下一步条件。

## 原则 6：功能范围与批次闭环

任务启动时必须限定本次初步适配场景。本次场景内的所有功能分支必须达到以下之一：已完成 OM 验证和接回、已失败并完成重规划、已形成 fallback 证据、已被用户确认排除。只完成单个子图、首批候选或局部 smoke，不构成本次适配场景完成；本次适配场景的主流程能端到端正常运行，才可作为初步适配完成。

`首批` 只是第一批执行集合，不是任务结束。当前批次完成接回和端到端验证后，若场景内仍有未闭环的主链候选，必须继续推进下一批。场景外候选记录为后续候选或暂不支持功能，并说明未支持原因、后续触发条件和风险，不阻塞本轮交付。

## 原则 7：验证门控标准

子图级和端到端验证必须使用标准化的通过/失败判据，不得每次临时发明阈值。具体门控指标见 [validation-gates.md](validation-gates.md)。
