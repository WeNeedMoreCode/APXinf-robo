# 验证门控标准

## 精度门控（子图级 ONNX vs OM）

先做契约门控，再看数值门控。契约门控包括：ONNX 与 OM 的输入数量、输入顺序/名称映射、输入 shape/dtype/layout、输出数量、输出顺序/名称映射、输出 shape 必须和 `Source-Side Subgraph Contract`、`Output Preservation Contract` 对齐。输出数量或 shape 不一致不是“精度差异”，不得接回主流程，必须回到 ONNX 导出、ATC 参数、动态推理 mode、输出 shape patch 或部署边界修复。

| 指标 | 通过 | 需复查 | 不通过 |
| --- | --- | --- | --- |
| cosine_similarity | >= 0.9999 | [0.999, 0.9999) | < 0.999 |
| max_abs_diff (FP32 OM) | < 1e-4 | [1e-4, 1e-3) | >= 1e-3 |
| max_abs_diff (FP16 OM) | < 1e-2 | [1e-2, 5e-2) | >= 5e-2 |

- "需复查" 区间的候选可继续推进但必须在端到端验证中重点关注
- "不通过" 且契约不一致时，必须回 Workflow 3/4 修复契约或重规划
- "不通过" 但契约一致时，不得直接退出；先按下面的偏差诊断流程决定是端到端复查、修复后重试，还是停止并报告

## 端到端验证门控

以原始实现（PyTorch/PaddlePaddle/ONNX Runtime）在相同输入上的输出为基准。具体指标取决于任务类型：

- 检测/分割：mAP 下降 < 1 个百分点，mIoU / mean IoU 下降 < 0.5 个百分点；高置信度保留结果不得出现类别变化、明显漏检/误检或 mask/box 明显错位。排序变化只在同类别、低置信度、接近阈值且后处理结果等价时可接受
- 分类/检索/排序/NLP 判别：accuracy 下降 < 0.5 个百分点；top-1 或业务使用的 top-K 集合不得发生用户可见变化。仅分数极接近的 tie-break 顺序变化可记录为可接受复查项
- OCR/语音/生成：WER、CER、BLEU 或同类客观指标下降 < 1 个百分点；文本、标签或结构化字段不得出现业务不可接受的语义变化。MOS、PESQ 等主观指标需人工确认
- 若无法量化：至少用 3 组以上代表性输入做定性对比，主输出不得出现用户可见错误；只影响未消费输出、padding / masked 区域或被后处理丢弃的低置信度候选时，记录证据后可继续推进

## 子图数值不通过后的诊断流程

当 ONNX 与 OM 输出数量和 shape 已确认一致，但数值门控不通过时，按以下顺序处理：

1. 复核比较本身是否公平：同一条真实输入、同一预处理、同一输入顺序、同一 dtype/layout、同一动态推理 mode/profile、同一 ONNX 候选、同一输出顺序。
2. 结合模型背景解释偏差来源：FP16 / 混合精度舍入、并行归约顺序差异、低幅值或低置信度输出放大相对误差、候选集合无序但语义等价、top-K / NMS / argmax / tie-break 排序扰动、padding 或 masked 区域差异、未被本轮功能消费的辅助输出差异、量化或优化融合引入的数值漂移。
   以上都是良性来源；偏差也可能来自 ATC 的静默 miscompile（ONNX Runtime 跑同一张图正确、OM 输出却结构性出错，典型是 clone+slice 写回段的常量 one-hot 丢失，见 FAQ 11）。判别信号：偏差远超融合噪声量级（>10% of |ref|max）、错误集中在特定构造模式的位置、ort-vs-eager 全对。此时不要按精度问题调参，先用 FAQ 11 的 mini 图隔离定位可疑段。
3. 若偏差只影响低置信度、未消费、被 mask/padding 覆盖、后处理会丢弃或排序等价的结果，可标记为“端到端复查候选”，允许先接回主流程，但必须在交付记录中写明风险和待验证点。
4. 若偏差影响高置信度主输出、类别/文本/结构化结果、状态缓存、后续会消费的特征或业务指标，必须先修复，不得以子图可运行为由继续交付。
5. 端到端复查不可接受时，回到修复：切换 ONNX 候选（`auto_optimizer` / `onnxslim` / `original`）、关闭或回退可疑优化、复核 ATC `precision_mode` / 混合精度策略、对敏感算子保留更高精度、修正 dtype/layout/preprocess/output mapping、调整动态 profile/mode、对 clone+slice 写回段做函数式重写（cat 拼接，值恒等，见 FAQ 11）、或回 Workflow 4 重规划边界。修复后重新做子图和端到端验证。
6. 修复仍无法达标时停止推进，向用户报告：契约状态、偏差指标、端到端影响、已尝试修复手段、仍不可接受的原因和建议 fallback / 后续方案。

## 性能验证

必须实测，不得仅引用理论值。报告至少包含：

- 子图级：单次 OM 推理时延（avg/p99，循环 >= 100 次）
- 端到端：完整流程时延（含前后处理）
- 与原始实现的时延对比和加速比
- 若加速比 < 1.0（变慢），必须分析瓶颈是在 OM 推理、数据搬运还是前后处理
