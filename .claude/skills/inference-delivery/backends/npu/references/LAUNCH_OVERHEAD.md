# 发射开销（launch postage）诊断与削减

**跨路径公共文件**（OM / torchair / 纯 torch_npu 都适用）：诊断与归因方法、否决案例与"先实测"原则是路径无关的；只有"并图吸收"的具体手法分路径（见该节注记）。

模型主体已图化（OM / torchair）但端到端仍慢、或两块板（新 / 老固件）同图性能差异大时读这个文件。核心问题形态：**图外残留的小算子串**（归一化、位置编码、mask 构造、轻量 encoder）每步发射几百次 kernel，单次任务极小，成本全在"发射邮费"上——这在 OM 双图和 torchair 双图之外的残留段上是同一个问题。

实测案例来自一个端到端规划模型的闭环推理项目（2026-09，310P3 主卡 vs 310P1 RC 板）；数字是当时的板况，方法论与量级判断可复用。

## 概念锚点：一次 NPU op 的三段成本

```
x = x + 1   (x 在 NPU)
 ├─ ① host 派发（dispatch）：Python 解释 + torch 派发层（校验/推 shape/选 kernel）
 │      与目标设备无关，CPU 快慢决定
 ├─ ② 投递（launch）：走驱动把工单写进 NPU 命令队列
 │      固定"邮费"（实测 ~9-35us/次），与任务大小无关——1 个元素和 1M 元素同价
 └─ ③ NPU 执行
```

小算子串耗时 ≈ (①+②) × op 数 + 执行。**图化 = 把几百个 kernel 打包成一次投递**，这就是为什么小算子串进图收益远大于它的计算量占比。老固件板卡的 ② 常比新板贵 2×（RC 17.5 vs DUO 8.8us），小算子串被等比放大——算力却可能是逐位相同的。

## 诊断工具族（三件套）

### 1. micro 探针：邮费五项

每个目标板跑一次，五项指标定义（timeit 块均摊，输出 us/op）。**可执行模板：`../scripts/bench_launch_probe.py`**——自包含（仅依赖 torch/torch_npu/numpy，无模型无数据文件），拷到目标板直接 `python bench_launch_probe.py`，两板各跑一次 diff 输出：

| 项 | 测什么 | 实现 |
|---|---|---|
| `cpu_micro` | ① host 派发 | CPU tensor 上连发 50 个 `x+1`，流水不 sync |
| `npu_micro_stream` | ①+② 派发+投递（流水） | NPU tensor 上同款连发，块尾一次 sync |
| `npu_small_mm` | 小 kernel 连发（接近真实小算子负载） | 小 matmul 连发 |
| `npu_big_mm` | ③ 纯算力标尺 | 1024³ matmul，host 占比可忽略 |
| `npu_micro_sync` | 单 op 全往返 | 每次发射后立即 sync |

读数法：
- **纯投递邮费 = npu_micro_stream − cpu_micro**（② 被单独隔离出来）
- big_mm 与 cpu_micro 是"理应无关"标尺——实验中它们不动，说明只动了投递路径，结论干净
- 输出直接给 us/op，不做事后换算（工具输出必须原样可贴）

### 2. 双板三锁归因法

两块板同款跑五项 + 分段数据后：

- **锁 1（算力）**：big_mm 两板逐位相同 → 算力零差，排除"老板算力弱"
- **锁 2（邮费）**：纯投递邮费差值（如 8.8 → 17.5us = 2.0×）
- **锁 3（受害段落点）**：每个受害段的板间比值应落在 **host 派发比（如 1.66×）与邮费比（2.0×）之间**——段内 host/NPU 发射的配比决定落点。全落区间内 → 归因闭合

实测案例（RC vs DUO）：锁 1 逐位同（221.75 vs 223.00us）、锁 2 2.0×、锁 3 norm 1.93×/pos 1.85×/route 2.11× 全在 [1.66, 2.0] 内 → "+40ms 全部来自 CPU 慢 + 发射邮费，算力零贡献"。反过来，如果受害段比值远超邮费比，说明还有别的因素，不要硬套这个结论。

### 3. 分段重放：真实输入逐段计时

脱离业务框架，用真实捕获输入重放一个 step，逐段计时。这一步**没有通用脚本**（捕获格式与模型强绑定），可复用的是方法：

- 在业务入口埋一个"首步转储"开关：把进入推理管线的原始输入 dict（CPU tensor）存盘，作为两板共同的重放基准
- **每段尾 synchronize 再读表**——异步 op 不排空，时间会记账到下一段；且"每段排空"与真实闭环的 sync 结构同构（图调用前排空、`.cpu()` 隐式 sync），测出来的段值才能外推闭环
- 捕获时机要与被测管线一致（若优化改变了数据入口位置——例如归一化移进图——capture 必须移到新入口之前，旧 capture 语义作废）
- 配一个 **CPU 标尺 probe**（固定 numpy + 对象属性访问负载）：无法重放的 CPU 段（如业务框架的对象处理）按两板 probe 比值外推

## 测量纪律（实测翻过车的三条）

1. **对"没反应"先查测量，再造理论**。一例：板 A 上某优化"无效果"，据此推演出一套"该板内存架构特殊"的解释并写进了文档——后来发现是**代码版本没生效**（detached HEAD 上 `git pull` 不动 HEAD，跑的还是旧代码）。分步实验前 `git log --oneline -1` 确认被测代码真的在场；解释现象之前先怀疑测量。
2. **对账一律同口径**：固定样本集（小样本的"中位数的中位数"方差可达 ±8ms/10%——5 场景两次同代码能差 8ms）、固定并发数（多 worker 共享一卡时单步中位含争抢，与独占口径不可比；wall time 的 sum vs concurrent 关系可以反推并发度）。跨轮比较注明口径。
3. **搬运成本板形态相关，勿跨板外推**：PCIe 卡与 SoC/集成形态的 H2D/D2H 定价完全不同，且方向未必符合直觉——实测一例中 SoC 形态板（RC）的搬运/sync 类反而**更贵**（往返 1.46×，micro_sync 可见），据此把"优化搬运动作的收益"按一块板的外推到另一块会错方向。两板各自的收益要各自实测（分步 commit、分步测）。

## 削减策略（按优先级；1 的手法分路径，2/3 路径无关）

1. **并图吸收（首选）**——小算子串进图，从"几百次投递"变"一次投递里多几组 kernel"。共性手法：
   - 归一化：mean/std 烤成图内常量；"全零行"mask 在原始数据上判、norm 后乘 `(~mask).unsqueeze(-1)` 置零（广播要对齐尾维）
   - 布尔散回（`x[valid]` / `x_result[valid] = x`）：全量计算 + valid 指示符置零——行独立的子结构严格等价；**注意上游 mask 语义**（per-row 置零 vs 整 batch 置零是不同语义，逐个核对）
   - 顺手把下游要用的派生量（如采样锚点）做成图输出，让下游彻底不依赖图外小算子

   **分路径注记**：
   - **OM（ONNX→ATC）**：atan2 有 ONNX 分解可用（别把 torchair 的限制套过来）；**slice 写回（`pos[..., i] = v`）必须函数式重写**（cat 拼接）——写回型节点 ATC 静默 miscompile，见 om/references/FAQ 11
   - **torchair（GE backend）**：部分 op 无 converter（实测 atan2），这类段只能图外保留 eager 或换算子改写；bool mask 散回同样被拒（动态 shape）
2. **循环不变量外提**：每步重复算的量（mask/编码）提为每步一次
3. **搬 CPU：先实测再动**——见下面否决案例 2

## 否决案例（实测数据，避免重蹈）

### 案例 1：`TASK_QUEUE_ENABLE=2` —— micro 变快，真实负载变慢

micro 层面纯投递邮费 11.5 → 4.8us（-58%），两个"理应无关"标尺（cpu_micro / big_mm）纹丝不动——看着非常像赢了。但分段重放（每段尾 sync）**全线变慢 19%**（sum 20.7 → 24.5ms）。

机理：任务队列把投递异步化，代价是**每次排空变贵**（队列交接 + 调度线程）。真实闭环是"发射一小段 → 图调用强制排空 → 再发射"的节奏，发射吞吐收益兑现不了，排空伤害全吃。

教训：**micro 指标与真实负载必须连跑对照**再下结论；判别"排空伤害"的口径就是带 sync 的分段重放。

### 案例 2：小算子串搬 CPU —— 11× 负优化

一条 ~40 op 的轻量 encoder 链（Mlp/Mixer，~40 MFLOPs）：NPU eager 4.5ms，**CPU eager 42-50ms（RC 空机实测，11× 慢）**；线程数扫描 1/2/4/8 全在 42-45ms（线程无关）；负载机上再被争用放大到 174ms。

机理：这条链在 NPU 上的瓶颈是**邮费**（几十次发射），在 CPU 上的瓶颈是**算力**（aarch64 上 GELU/LayerNorm/小 GEMM 吞吐 ~1 GFLOP/s 量级）。两头的瓶颈类型不同。

教训：
- **"NPU 上是邮费瓶颈" 推不出 "CPU 上更便宜"**——不能拿 NPU 的 host 派发单价（~17us/op）外推 CPU 执行单价（实测可到 ~1ms/op）
- 搬 CPU 前先在**目标板的空机**上实测 CPU eager（负载机上的数字还会被争用放大 4×，更不能看）
- 并图吸收后这类段在 RC/DUO 两板同价（各 ~1ms 级），比搬 CPU 干净

## RC 类（老固件/集成形态）板卡的差异画像——诊断起点先验

来自一次完整双板实测案例的泛化（310P3 主卡 vs 310P1 RC 板，2026-09，端到端规划模型闭环推理）。**这是先验假设不是结论**：单块板可能不符合，每项用对应探针验证后再定。

| 嫌疑项 | RC 类板的典型表现（先验） | 验证探针 | 高频误区 |
|---|---|---|---|
| NPU 算力 | 同代核心**逐位同**，通常零差——第一个要排除的项 | `npu_big_mm` | 直觉"小板=算力弱"，把小算子串的慢误归因为算力 |
| 发射邮费（launch） | 老固件驱动路径慢，常见 **~2×**；小算子串（几十~几百 op 的前后处理）被等比放大——**RC 类板最大嫌疑** | `npu_micro_stream − cpu_micro` | 把它当算力问题去调精度参数 |
| host CPU | 常配弱 CPU（案例实测 1.34×），作用于**全部 host 代码**（前后处理/对象处理，含 CPU op 的 dispatch——dispatch 随 CPU 整体缩放，不是独立因素） | cpu_probe 标尺（numpy+对象访问固定负载） | 只盯 NPU 侧查，漏掉 CPU 段的板间差 |
| 搬运/往返 | 可能更贵（案例 sync 往返 1.46×）——**勿因"SoC 集成=共享内存=搬运便宜"的直觉跳过实测** | mixed 分段 d2h/h2d、`npu_micro_sync` | 拿另一块板的搬运成本外推本板 |
| 在线编译 | tbe 通道可能不可用，新形状触发即 500002/E40021 | 见 torch_npu/references/rc_device_toolkit 工具 5 | — |

**处置先验**（画像验证后高概率有效的方向）：

- 小算子串 → 并图吸收（RC 的收益按邮费比放大，常比主板赚更多）
- host↔device 搬运中转（host 产数据上卡、图调用再搬回）→ 直接删（host 直通）；两板收益各自实测
- 纯 host 代码 → 削绝对工作量，两板同赚、RC 按 CPU 比放大
- 图化到位后两板图执行应同价——仍不同价说明图内还有逐发射段，回削减策略

诊断顺序建议：先跑 micro 五项（半分钟出全画像的量化版）→ 按上表排除/确认 → 分段重放定位受害段 → 逐项处置。

## 战果参考（案例锚点）

同一案例三轮优化：RC 板单步 121.3→90.0ms、主板 80.6→70.5ms，板间差距 40.7→19.5ms，精度全程持平。拆解即上表画像的验证过程：算力零差（big_mm 逐位同）、发射 2× 被图化消除（图执行归同价）、搬运中转被删除（RC 反而赚更多）；残差与"CPU 1.34× × host 代码量"吻合，判定为 host 执行速度差（换 host 才能解决的物理差）。
