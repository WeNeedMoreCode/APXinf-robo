# 调试验证方法论

根据情况选方法，前提条件不满足的不要用：

```
"不知道问题在哪"                       → 方法一：全链路诊断
"已定位到某模块，不知道哪步错"          → 方法二：最小化验证
"有工作/坏版本，差异可逐个剥离"         → 方法三：反向排除法
"问题只在某配置/平台出现"               → 方法四：双路径对比
```

## 方法一：全链路诊断

**核心动作**：全量系统跑一遍，在关键节点插桩观察，定位问题在哪个模块。

### 什么时候用

- 不知道问题在哪，需要先确定大方向
- 系统有多层/多模块，不确定是哪一层的错
- 作为调试的**起始点**，之后接最小化验证做细定位

### 怎么做

1. 让完整系统跑一遍，不要拆
2. 在**数据转换边界**插入诊断输出：
   - 输入读取后 → 输出前几个元素，验证读到了什么
   - 计算完成后 → 输出中间结果
   - 循环/条件后 → 输出计数器和状态
   - 写回外部前 → 输出要写入的值
3. 每步只输出少量关键数据，避免日志过大
4. 用哨兵值预填输出区域，区分"没执行"和"执行了但结果错"

### 为什么不要先拆

把系统拆成 5 个独立测试，如果前 4 个全过、第 5 个失败，你只知道第 5 步有问题。但如果问题其实是**第 3 步的输出格式不对，导致第 5 步的输入异常**——拆开后的单步测试看不到跨步依赖。而且拆 5 套代码本身就是成本。

### 和最小化验证的关系

全链路诊断是**前置步骤**：
- **全链路诊断**告诉你"问题大概在哪个模块"
- **最小化验证**告诉你"这个模块里具体哪一行/哪个条件错了"

两者结合：先粗定位，再细定位。

## 方法二：最小化验证

**核心动作**：针对已定位的模块，逐步输出每步状态，二分查找具体失败的步骤。不猜测原因，只输出数据，让数据说话。

### 什么时候用

- 全链路诊断已经定位到某个模块（通常配合使用）
- 构建最小复现来隔离 bug
- 集成前验证新组件能工作

### 怎么做

#### 1. 列出每一步，包括无聊的

不要跳过"显然没问题"的步骤。上下文初始化、资源分配、依赖准备——这些往往是真正的罪魁祸首。写代码之前先列出来。

```
步骤 1: 初始化运行时上下文
步骤 2: 分配 buffer A
步骤 3: 分配 buffer B
步骤 4: 执行操作 X
步骤 5: 读回结果
```

#### 2. 每步立即输出自己的状态

每步之后，输出：尝试了什么、返回码或结果、是否成功。

不要批量输出。不要等到最后。不要把多个步骤压缩成一个状态。

坏：
```
return (step1() == OK && step2() == OK && step3() == OK) ? 0 : -1;
```

好：
```
step 1: init context ... ret=0
step 2: alloc buffer ... ret=0
step 3: launch kernel ... ret=107002  <-- 问题在这
```

#### 3. 区分"没执行"和"执行了但结果错"

用哨兵值预填输出 buffer（如 0xFF 字节，对 float 读作 NaN）。这样能区分：
- Buffer 还是哨兵值 → 该步骤没执行
- Buffer 是零 → 步骤执行了但产出为零
- Buffer 是预期值 → 步骤正常

#### 4. 验证假设后再往下走

如果步骤 3 依赖步骤 2 成功，先检查步骤 2 的结果再继续。失败的步骤后面跟着更多步骤会产生混乱的级联失败。

#### 5. 把通用前置步骤封装成可复用的基础设施

复杂工程中，运行时初始化、资源分配等会被反复用到。封装成带日志的工具函数/脚本，调用时扫一眼就知道前置条件是否满足。

### 如何使用结果

拿到逐步输出后：

1. **找到第一个失败的步骤。** 之后的所有结果都不可靠——忽略。
2. **只修那一步。** 不要碰其他东西。
3. **重新跑最小测试。** 验证修复。
4. **然后才**加复杂度或进入下一层。

这是二分查找应用于调试：每步的输出把搜索空间砍一半。

## 方法三：反向排除法

**核心动作**：从能工作的版本出发，每次只去掉一个东西，直到复现失败，定位根因。

### 什么时候用

- 你有一个能工作的版本和一个不能工作的版本
- 两个版本之间的差异**可以逐个剥离**（每个差异独立，互不依赖）。如果改动互相耦合则不适用
- 正向分析看不出两个版本之间哪个差异是根因
- 全链路诊断和最小化验证无法区分"代码逻辑错"还是"编译器行为异常"

### 怎么做

1. 从**能工作**的版本出发（不是从坏的版本出发）
2. 每次只去掉一个差异（一段代码、一个 buffer、一个 API 调用）
3. 每次去掉后编译运行，看结果：
   - 仍然 PASS → 去掉的东西不是根因，继续去掉下一个
   - FAIL 了 → 刚去掉的东西就是根因（或者与根因强相关）
4. 找到根因后，在生产代码中针对性修复

### 关键约束：每次只去掉一个东西

**这是反向排除法的核心纪律。** 一次去掉两个或更多东西，如果结果从 PASS 变成 FAIL，你不知道是哪一个导致的。如果结果仍然 PASS，你以为都无关，但实际上可能一个有关一个无关，正好互相抵消。

### 和正向排查的区别

| | 正向排查 | 反向排除法 |
|---|---------|-----------|
| 起点 | 坏的版本 | 好的版本 |
| 动作 | 加东西（猜修复） | 去东西（缩窄范围） |
| 失败模式 | 猜错了方向，白改 | 一次去太多，丢失定位精度 |
| 适用 | 大概知道问题在哪 | 两个版本看不出差异 |

### 实例

一个有详细日志的版本 PASS，去掉日志的版本 FAIL。差异包括：日志变量声明、请求计时、响应体写入等。

从工作版本出发逐个去掉：
1. 去掉请求计时 → PASS
2. 去掉响应体写入 → **FAIL**

定位到：响应体写入不是在"写日志"，而是**意外地触发了数据序列化**，修复了下游的数据格式问题。去掉它后格式错误暴露。

（领域相关的完整实例见 `references/reverse_elimination_example.md`）

## 方法四：双路径对比验证

**核心动作**：同一输入走两条路径（参考路径 vs 待测路径），逐层对比中间输出，定位精度/行为差异的来源。

### 什么时候用

- 模型跨硬件平台移植（GPU → NPU/ROCm/CPU）
- 编译优化前后验证数值一致性（eager vs compiled、torchair vs 原生）
- 数据类型变更后验证精度（fp32 → fp16/bf16）
- 有一个已知正确的参考路径，需要量化新路径的偏差

### 怎么做

#### 1. 固定输入

两条路径使用**完全相同**的输入数据。最可靠的做法是把输入序列化到磁盘（`torch.save`），两条路径各自加载。避免"各自构造看似一样的输入"——微小的构造差异（随机种子、预处理顺序）会引入与待查问题无关的噪声。

#### 2. 逐层插桩

用 forward hook 在每个 block/layer 捕获中间输出。不要只看最终输出——最终输出的误差是所有层累积的结果，无法定位源头。

```python
# 逐层 hook 捕获中间输出
outputs = {}
def make_hook(name):
    def hook(module, input, output):
        outputs[name] = output.detach().cpu()
    return hook

for i, block in enumerate(model.blocks):
    block.register_forward_hook(make_hook(f"block{i}"))
```

只输出少量关键数据（shape、dtype、前几个元素），避免日志爆炸。如果层很多（如 28 层 transformer），设置只输出前 N 步的日志。

#### 3. 逐层对比误差

计算每层输出的误差指标：

- **MSE**（均方误差）：对大偏差敏感，适合定位"哪里出了大问题"
- **MAE**（平均绝对误差）：对异常值不敏感，反映整体偏差水平
- **余弦相似度**：只看方向不看大小，适合判断语义是否保持

一般用 MSE 定位问题层，用 MAE 评估整体精度是否在可接受范围（如 3% 以内）。

#### 4. 分析误差模式

- **误差突然跳升** → 该层有问题（算子实现差异、dtype 转换、attention 机制不同）
- **误差逐层线性累积** → 浮点精度的自然累积，不是代码 bug
- **第一层就有误差** → 检查输入预处理或 embedding 层
- **所有层误差比例一致** → 可能是全局原因（硬件 fp16 实现差异）

#### 5. 下钻到子模块

定位到有问题的层后，在该层内部再插桩到子模块（attention、MLP、norm），进一步缩小范围。方法同上：hook 子模块 → 对比输出 → 找到第一个有显著差异的子模块。

#### 6. 引入 CPU 作为高精度参考

当对比两个硬件平台时，两者都可能与"理想"结果有偏差。用 CPU 跑同一路径作为更高精度的参考（CPU 的 fp16 运算内部用 fp32），可以判断：

- 两条路径的差异是硬件 fp16 实现不同，还是代码 bug
- CPU → 平台 A 和 CPU → 平台 B 的误差各自多大，判断哪条路径更接近"正确"

如果 CPU → 平台 A 和 CPU → 平台 B 的误差量级相同（如都在 0.01% 左右），说明两条路径都在正常精度范围内，差异来自硬件 fp16 舍入方式不同，不是代码问题。

#### 7. 对拍非数值字段（键存在性 / mask / dtype）

数值全等 ≠ 行为等价。逐元素 diff 之外，必须对拍每个字段**是否存在**、mask/标志位、dtype、设备布局。实测案例（NPU VLA 移植）：给占位相机补零图后，零图 ×2−1 恰好等于参考实现的全 −1 占位图——图像逐像素全等、所有数值对拍全绿——但"键存在"本身翻转了下游的 mask 位（1 vs 0），一个假 embedding 混入 cross-attention，闭环成功率 0/10。分岔藏在一个 bool 里，数值 diff 永远看不见它。

对拍两层结构的 batch/dict 时，报告"只在 A / 只在 B"的键和 mask 类字段，与报告 maxdiff 同等重要。

#### 8. 对拍基准必须是被复刻链路的真实代码

不要用"看起来等价"的另一条路当基准。案例：模型仓库自带的离线推理脚本吃**数据集帧**（已归一化、已翻转的域），而真实评测链吃**环境渲染帧**（uint8、未翻转）——用前者对拍会漏掉后者特有的全部转换语义。找到评测链实际调用的那个函数（本例是 `LiberoProcessorStep._process_observation`），对拍它的输入输出，而不是一个更方便的替身。

#### 9. 降低单次对拍成本：轻量化对拍循环

对拍的价值随迭代次数增长，单次成本决定迭代次数。把整条链按资源需求分层，下层绿了才升上层：

| 层 | 资源 | 单次成本 | 手段 |
|---|---|---|---|
| 翻译层（obs→batch） | 纯 CPU | 秒级 | 只加载 config 不加载权重；`object.__new__` 绕过重量级 `__init__`；输入固化到磁盘 |
| 推理层（batch→输出） | 需加速器 | 分钟级 | 单帧对比，接受 ulp 级（硬件非确定性） |
| 闭环层（输出→成功率） | 加速器+环境 | 十分钟级 | 时序对齐找第一个分岔：同 seed 双路径逐步记 `(obs_hash, action, 队列状态)` 并排 diff |

实测：翻译层对拍从"整集 NPU 跑 3 分钟模型加载 + 1 分钟/集"压到 40 秒/次后，一个下午完成了此前 8 小时没定位到的根因。

### 和其他方法的关系

双路径对比是**跨配置的全链路诊断**。当全链路诊断发现问题只在某个配置/平台出现时，用双路径对比找出两个配置在哪一步开始分叉。

全链路诊断回答"哪个模块有问题"，双路径对比回答"两个版本在哪个模块开始不同"。

## 四种方法的交互关系

```
调试开始
  │
  ▼
全链路诊断（全量跑 + 关键节点插桩）
  │
  ├─ 定位到某模块 ──→ 最小化验证（逐步输出，二分查找）
  │                      │
  │                      └─ 找到失败步骤 → 修复 → 验证
  │
  ├─ 无法区分差异（有 working/broken 两个版本）
  │    │
  │    ▼
  │  反向排除法（从工作版本逐个去掉差异）
  │    │
  │    └─ 找到根因 → 修复 → 验证
  │
  └─ 问题只在某个配置/平台出现
       │
       ▼
     双路径对比（同输入走两条路径，逐层 hook 对比）
       │
       ├─ 误差逐层线性累积 → 硬件精度差异，非代码 bug
       ├─ 误差在某层跳升 → 下钻该层子模块
       └─ 找到差异来源 → 修复 → 验证
```

**全链路诊断 + 最小化验证**是总分结合，先粗后细，应该配合使用。

**反向排除法**是独立路径，当正向方法无法区分差异时启用。

**双路径对比**是跨配置的诊断手段，当问题只在特定环境/配置出现时启用。

## 通用原则

以下原则适用于所有三种方法。

### 关键结果出来后立即记录

最小测试产出确定性结论（pass 或 fail）时，**立即记录**——在设计下一个测试或提出修复方案之前。原因：

1. **上下文丢得很快。** 测试迭代之间代码变了、脚本变了、产生结果的确切条件变得不可恢复。原始数据 + 解读必须趁新鲜时捕获。

2. **防止乐观记录。** 测试只显示 GetValue 返回了错误值时，很容易写成"GetValue 读错了地址"。实际验证过的事实是"GetValue 返回错误值；scratch GM 数据经 host readback 验证正确。"

3. **分离事实和假设。** 记录测试测量了什么，不是为什么失败。"为什么"是假设，下一个测试应该验证或否定它。

**该记什么**：
- 测试设计（测什么，怎么隔离变量）
- 原始输出数据（实际值，不只是 pass/fail）
- 一句话验证结论
- 还有什么未知

**不该记什么**：
- 假设写成结论——"X 是因为 Y"（没验证过就当事实记）
- 方案写成要求——"应该修 Z"（根因还没确认就下结论）

**可以记假设，但要标明是假设**：记成"怀疑 Y 导致了 X，下一步验证"。

### 警惕掩盖根因的 workaround

当你加了一个修复（reset、补丁、retry）测试改善了但没有全过，这个修复可能在掩盖真正的 bug 而不是解决问题。

```
Bug: 每轮迭代后某个值不对
"修复": 每轮迭代后把这个值重置为默认值
结果: 测试从 15/264 变成 243/264 —— 看起来有进展！

真正根因: 这个值被另一段代码意外覆盖了，重置只是补了被覆盖的值
真正修复: 修复那段覆盖代码
结果: 全量通过
```

当修复只是部分有效或在其他地方引入新失败时，停下来问："我是在治症状还是治病？"

### 有状态组件：用例边界必须复位

单用例各自全绿、但**序列组合**才出错时，查组件内部状态跨用例残留：队列、缓存、随机数生成器、上一次调用的临时替换（monkeypatch 忘了恢复）。实测案例：推理策略的内部动作队列跨 episode 存活，每集开头执行上一集尾部最多 49 个陈旧动作；旁证是只有首集（队列干净）和前集提前结束的集（残留少）能成功。官方参考实现在边界处 reset——复刻时逐行核对参考实现的**边界处理**，不止核对计算逻辑。

### 修复后必须重新验证

定位到根因并修复后，**必须重新跑相同的诊断测试**确认修复有效。如果仍 FAIL，继续隔离下一个失败点。

```
1. 诊断测试 → FAIL → 定位根因
2. 修复
3. 重建 + 重新跑诊断测试
   → PASS → 应用到生产代码，跑全量测试
   → FAIL → 回到步骤 1，继续隔离
```

### 反模式

**大杂烩返回码**：一个函数做了 7 个操作然后返回 0 或 -1。返回 -1 时你不知道哪个操作失败了。

**"这应该没问题"跳过**：因为"很简单，不可能失败"而跳过某步的诊断输出。你跳过的那步就是正在失败的。

**端到端唯一测试**：跑完整个流水线只检查最终输出。最终输出错了你有 N 个可能的故障点，零信息。

**假设级联**："buffer 分配成功了（假设），所以 kernel launch 应该也成功（假设），所以结果应该正确（假设）。"最终结果错了你要检查 3 个假设，没有数据。

**改错了地方**：测试失败时直觉是修改被测对象。但如果失败在更早的步骤（运行时初始化、资源分配），所有修改都是白费。
