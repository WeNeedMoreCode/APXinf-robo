# Pedagogy：学习路径与自测

## 何时读取

当用户要学习、复习或理解技术主题，要求创建/改写学习笔记、补齐“为什么”，或现有文档直接抛出结论、公式和实现时读取本文件。

## 从读者已有知识出发

从对话和文档推断读者已经掌握、刚刚忘记和当前卡住的内容。信息不足时采用保守假设：读者知道基础名词，但不知道新结构为什么出现，也不能自行补齐公式中间步骤。

把学习目标写成可验证动作，例如：

- 用自己的话解释一个设计解决了什么问题；
- 从基线方案推导出新方案；
- 区分两个相似概念；
- 根据约束预测代价或失败模式。

避免只写“了解 X”。

## “是什么、怎么做、为什么”三层门禁

学习文档不能只替设计者辩护“为什么这样设计”。读者必须先建立对象和结构，才能理解原因；还必须亲自跟完一次运行过程，才能把术语还原成机制。

### 第一层：是什么——建立结构地图

一个新主题或核心组件首次出现时，先回答：

- 它属于哪类东西，是模型层、训练方法、数据结构、运行时系统，还是评测指标；
- 它位于整个系统的哪里，上游和下游分别是谁；
- 它接收什么输入，产生什么输出，会保存或修改什么状态；
- 它由哪些子部件组成，哪些旧部件被替换，哪些保持不变。

“是什么”不是只给一句字典定义。较大的主题应先给结构图、层级图或组件表，让读者能指出每个名词在图上的位置。不要先问“为什么需要 X”，却还没告诉读者 X 到底是什么。

### 第二层：怎么做——跑通一次具体过程

机制说明不能停在“编码、压缩、路由、融合、校正”这类动词。每一步都写明：

1. 当前手里是什么对象，形状或最小示例是什么；
2. 哪个部件对它执行了什么操作；
3. 这一步产生什么中间结果，保存在哪里；
4. 下一步具体使用哪个结果；
5. 最终输出交给系统中的谁。

核心机制至少选择一种可追踪载体：小数值例子、带形状的数据流、伪代码、状态变化表或完整调用链。展示中间状态，不只画“输入 → 黑盒名称 → 输出”。公式必须对应到这些步骤；读者应能指出公式每一项是在读取、修改还是输出哪个对象。

需要用图示承载结构或过程时，读取 `diagramming.md`，按目标关系和公式需求选择 Mermaid、表格或独立公式，并提供必要的语义后备。

实现深度以“读者能否凭文档手工走一遍或写出骨架伪代码”为准。无法公开的实现细节要明确标为未知，不能用含糊动词把证据缺口伪装成解释。

### 第三层：为什么——解释选择和取舍

结构和过程有了落点后，再完整回答：

1. 原来的做法是什么；
2. 它在什么约束下出现具体问题；
3. 新方案改变了哪一步；
4. 为什么这种改变能缓解问题；
5. 得到了什么收益，又付出了什么代价；
6. 为什么不用相邻的替代方案，哪些问题仍未解决。

教学顺序可以因主题微调：有时先用旧方案的问题制造动机，再展开新方案的细节；但在任何“为什么需要 X”之前，至少先给出 X 的一句话身份、位置和目标。关键转折要回答“为什么会想到这里”，不能取代“它是什么”和“它实际怎样运行”。

## 相邻章节也必须有因果关系

全文包含了正确的知识点，不代表阅读路径已经成立。每个新章节都应承接上文刚刚产生的问题，或者在开头明确交代“为什么现在要谈它”。

- 数字、术语或争议第一次进入标题前，先在上文引出；如果必须从标题开始引入，首段立即说明它的来源、意义以及与前文的关系。
- “回答为什么”是正文必须补齐因果的要求，不是把每个标题都改写成问句。标题优先描述本节真正完成的学习任务，只有读者此时自然会提出该问题时才使用问句。
- 问句标题要能脱离作者脑内上下文独立成立，并符合自然语言习惯。不要把审稿备注写成标题，例如“X 不能怎样理解”；改成“X 究竟指什么”，再在正文说明它不代表什么。
- 证据边界和防误读说明应附着在已经介绍过的主张之后。不要在读者尚未见过某个说法时突然辟谣，也不要让核验备注抢在概念主线前面。
- 章节转换无法由上一段自然推出时，增加一句桥接：总结刚解决了什么，再指出下一个尚未解决的问题。若加桥接仍显得牵强，应移动、合并或删除该章节。

用户的追问首先是**缺口诊断信号**，不是可以原样粘贴进文档的标题。把追问沉淀为正文时：

1. 判断追问暴露的是身份、系统位置、输入来源、执行过程还是设计原因缺失；
2. 回到读者第一次依赖这项知识的位置补足前提，而不是只在当前光标处追加一段问答；
3. 用稳定的学习任务命名章节，例如“输入参数的生成：先进行局部混合”，不要保留依赖聊天现场的“这个参数从哪里来”；
4. 修改后假设读者从未看过对话，只读相邻标题和首段；如果仍需知道用户此前问了什么，说明修订痕迹尚未清除。

追问形成的解释较长或包含可选旁支时，不要默认全部就地或全部后置；读取 `progressive-disclosure.md`，按其中的前向依赖、最小充分和打断成本标准分层。

写完后执行一次**冷读检查**：只读目录、每节标题以及各节首尾段，逐节确认读者知道“这里说的 X 是什么、它为何此时出现、它与上一节有什么关系”。发现需要依赖作者搜索过程或未写出的前提才能理解时，视为结构缺陷，而不是读者知识不足。

再执行一次**遮名检查**：把组件名称暂时遮住，只看输入、操作、中间状态和输出。如果剩下的内容不足以区分它与其他组件，说明“怎么做”仍然只是在换词复述名称。

## 新概念和公式

新概念首次出现时依次说明：它是什么、作用对象是什么、原方案为什么不够、它改了哪一步、最小例子怎样运行、与相似概念哪里不同。

公式用于压缩已经讲通的逻辑，不用于代替逻辑：

- 公式前定义符号、下标、上标和形状；
- 推导时解释每一步依据；
- 公式后翻译成执行流程；
- 类比后指出真实机制以及类比失效的位置。

在保留公式前执行一次**依赖闭合检查**：枚举公式中第一次出现的符号、函数、算子和模块名，不能只定义字母而跳过 `Norm`、`Conv`、门控、路由等调用。对每个非基础算子至少说明：

- 它位于核心机制之前、之中还是之后，上游输入和下游消费者分别是什么；
- 它实际作用于哪个对象和维度，并产生什么中间结果；
- 它是否读取窗口、历史状态、缓存或其他未写在简式中的输入；
- 它属于核心数学、神经参数生成还是执行优化，避免把完整模块外围处理误写成核心递推的一部分；
- 如果简写看起来是逐点函数，而真实操作需要一段序列、一个批次或历史窗口，展开一次真实操作，再回到简写。

这项检查的目标是让公式的依赖关系在文档内闭合：读者不需要凭论文惯例猜出某个算子“应该是从哪里接进来的”。

## 复习要点

较完整的学习笔记在主体之后设置“复习要点与自测”。复习要点不复制目录，而是提炼：

- 知识依赖顺序与主因果链；
- 易混概念的区分依据；
- 关键公式分别描述哪个过程；
- 收益、代价与证据边界；
- 隔一段时间后应按什么顺序复习。

短答、速查表或用户明确不要练习时省略。

## 自测题

题量与内容规模匹配，不为凑数出题。优先覆盖：

- 结构：组件位于哪里，输入、输出和状态分别是什么；
- 过程：给定小输入，逐步写出中间状态和最终去向；
- 原因：为什么需要这个设计；
- 对比：两个相似概念是不是一回事；
- 反事实：去掉某个部件会怎样；
- 权衡：收益是否值得复杂度，证据是否充分。

完整学习文档的题目不能被“为什么”垄断；至少覆盖一次结构复述和一次过程推演。避免只问全称、孤立数字或能从上一句话直接抄出的事实。题目与答案的具体排版遵循 Presentation 层。

## 沉淀后续追问

用户围绕自测题追问时先回答当前疑问；用户要求落盘后，把讨论归入对应答案：

1. 保留用户原来的直觉或质疑；
2. 指出其中成立的部分；
3. 修正不准确的边界；
4. 补齐原因到机制的推导；
5. 给出具体例子或反例；
6. 说明代价、局限和证据强弱；
7. 收束为可复述的标准答案和一句话记忆。

如果追问暴露正文第一次讲解时缺少必要前提，还要回头补正文；不要让读者必须做完题才第一次见到核心概念。

## 教学质量检查

- 没有“直接抛观点，再用术语解释术语”。
- 核心对象说明了类别、系统位置、输入、输出、状态和子部件，而不只有一句定义。
- 核心过程至少有一次可逐步追踪的执行示例，关键动词对应明确对象和中间结果。
- 每个关键转折都有动机或通用模式支撑。
- 各节标题描述稳定的学习任务而不是复刻用户追问；新数字和概念有前文铺垫，相邻章节不依赖对话现场或作者未写出的思路跳跃。
- 公式中的非基础算子已说明真实输入、作用维度、所属阶段和隐藏状态，没有用紧凑记法掩盖必要依赖。
- 例子展示了中间状态，而不只给输入和结论。
- 对比明确操作对象、维度、阶段和目标。
- 读者能够在不背原句的情况下复述主因果链。
