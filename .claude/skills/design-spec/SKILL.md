# 设计说明书生成器

生成结构化的软件系统设计说明书，包含 Story 描述、上下文、功能分解、类图、实现思路、时序图和流程说明。

## 输出格式

单个 `.md` 文件，使用 Markdown + Mermaid 图表。文件名建议 `<项目名>_设计说明书.md`。

## 文档结构

按以下顺序组织，每个章节都是一级或二级标题。如果某个章节对当前项目不适用，可以跳过并说明原因。

### 1. Story 描述

一句话说清系统做什么。格式：

> [系统名] 是一个 [类型] 系统。系统接收 [输入]，通过 [核心过程]，输出 [结果]。

要点：
- 用非技术人员能理解的语言
- 只说"做什么"，不说"怎么做"
- 控制在 1-2 句话

### 2. Story 上下文

系统的运行环境和约束，用无序列表：

- **应用场景**：系统用在什么场合
- **输入**：具体列出输入项及其含义
- **输出**：具体列出输出项及其含义
- **运行环境**：硬件、操作系统、依赖等
- **性能目标**：有具体指标的写具体指标
- **核心约束**：设计上不可变更的限制

根据项目实际情况增减条目，不要求每条都有。

### 3. 功能点分解

将系统功能按类别分组，每个功能点用编号列表。格式：

```
### 类别名
1. **功能名称**：一句话说明
2. ...
```

分组逻辑：
- 按技术层面分组（如：算子适配、编译优化、推理加速）
- 或按业务模块分组（如：用户管理、订单处理、支付集成）
- 选择让读者最容易理解的方式

如果功能点有量化的优化效果，在末尾附一个汇总表格。

### 4. 类关系图（Mermaid classDiagram）

用 Mermaid classDiagram 画出系统的类结构和依赖关系。

画法要点：
- 每个类列出关键的属性和方法（不用全部，选对理解架构重要的）
- 用注释标注特殊状态（如 `[已移除]`、`select_layer=16截断`）
- 关系用箭头标注（`-->` 表示依赖，标注属性名）
- 从调用者到被调用者从左到右、从上到下排列
- 如果类太多，分多个图（如"高层类图"和"子模块类图"）

### 5. 功能实现思路

每个主要功能点用 2-5 句话说明实现的关键思路。重点讲"为什么这么做"而非"做了什么"。

格式：
```
### N. 功能类别名

1-2 句说清核心思路。如果有多种可选方案，说明为什么选了这个。
必要时用简短的代码片段说明关键模式。
```

与功能点分解的区别：功能点分解是"做了什么"的列表，实现思路是"为什么这么做"的叙述。

### 6. 推理/调用链（Mermaid sequenceDiagram）

用时序图展示核心流程的调用顺序。

画法要点：
- participant 用简短的别名（如 `BB` = Backbone），但旁边注明全名
- 按时间顺序从上到下排列
- 标注耗时（如果有的话）
- 用 `Note over` 标注阶段名（如 `Step 1: 预处理`）
- 同名方法要区分（用类名前缀或注释标注是哪个类的方法）
- 用实线箭头（`->>`）表示调用，虚线箭头（`-->>`）表示返回

### 7. 流程说明

用时序图对应，按阶段展开说明每个步骤的具体内容。格式：

```
### 阶段名（设备/位置，耗时）

具体说明：
- 子步骤 A：做什么
- 子步骤 B：做什么
- 输出什么
```

### 8. 内部数据流（Mermaid flowchart，可选）

对于有复杂数据流转的系统（如多模块之间有数据拼接、注入、转换），用 flowchart 画出来。

画法要点：
- 用 `subgraph` 按模块分组
- 用不同样式的箭头区分主流程（实线）和辅助数据（虚线）
- 在节点上标注数据形状（如 `image_embeds (1024 tokens)`）

如果数据流简单（线性传递），跳过此章节。

## 附录章（可选，文末平级排列）

涉及相应内容时启用，两个附录章与正文编号平级、放文末：

- **术语表**：领域缩写与非常见概念，词条式集中定义。双向锚点：正文首现处挂 `[词](#term-…)` 链接并放 back 锚，词条尾 `[↩ 返回](#back-…)`——读者就地跳到定义、看完跳回原文
- **接口速查表**：外部系统/框架的关键类型与接口，词条式收录——数据结构（字段、内部容器）、关键方法签名（接收什么、返回什么、数据是被送进来的还是主动取的）、来源时机（每步新交 / 初始化一次性给）、消费方式；含系统的入口调用（外部框架怎么调进来）。定义从源码实证（grep 上游库），不凭记忆。与术语表的分工：术语表讲概念（是什么），接口速查表讲结构（长什么样、怎么调）。锚点机制同术语表（`#iface-…` 双向跳转）
- 正文叙述不堆类型细节——保持画面化讲解，类型/接口/结构放表、首现处挂链接跳转

当设计对象是基于上游仓库的适配/移植/二次开发时，设计说明书**分成两部分**，不混写。混写容易把上游行为误记到本仓名下（或反过来），审阅者也难以一眼看清适配面；结构性分离比逐类标注更不容易出错。

- **第一部分：原仓设计**——上游系统的 Story、组成与流程。从简，作为背景：只写到理解第二部分所需的最小程度，细节指向上游文档/代码，不在本文展开。但仍按 design-spec 精神配**最小图集（至少类图）**，只是粒度组件级；上游的类/方法清单优先从 git 基线 commit（本仓首笔提交的父）用 `git show <基线>:<文件>` 抽取实证，不凭记忆或当前代码反推——当前代码里的方法可能已是适配后加的
- **第二部分：本仓设计**——适配后的完整设计（功能分解、类图、实现思路、时序、数据流全部在此部分），是文档主体。引用上游组件时指向第一部分，不重复展开；本部分图中出现的上游类默认是"被改过/被引用"的当前状态

两部分各自独立编号章节。如需精确到"哪个类改没改"，可在第二部分类图后附来源对照表（`上游原样 / 改自上游 / 本仓新增 / 本仓外移`）作为桥接——但区分的骨架是两部分的结构分离，对照表只是补充，不替代。
- **实现思路（§5）**：只写适配修改的 why；上游设计动机仅在影响适配决策时一句带过
- Story、时序图里出现的上游组件，首次提及时注明"上游组件"，不展开

## 神经网络模型结构图

模型层结构 + tensor shape 流动（区别于软件类图）用 `torchview.draw_graph(model, input_data, depth=1)`：depth 控制主干/细节，节点可点击下钻，shape 来自实测 forward；大模型分子模块分别出图。notebook 里交互探索用 torchvista（一行代码、拖拽/展开折叠；2026-09 查 761★、活跃维护，易用性未实测），出静态图进文档用 torchview，二者分工。trace 不需要真权重——config-only 随机初始化即可（shape 与数值无关）。参数表用 `torchinfo.summary`；Netron 是算子级，不适合看主干。

## 工作流程

生成设计说明书时，按以下步骤执行：

1. **探索代码库**：阅读核心模块的代码，理解类关系、调用链、数据流
2. **生成类图**：先画 classDiagram，这是理解系统的基础
3. **生成时序图**：基于类图画出核心流程的 sequenceDiagram
4. **补充文字说明**：Story、上下文、功能分解、实现思路、流程说明
5. **检查完整性**：确保每个类在类图或时序图中有体现，文字说明和图表一致

## 注意事项

- Mermaid 图中避免过长的文本，超过 20 个字符的类名/方法名用缩写或换行
- 类图不需要列出所有属性和方法，选对理解架构关键的即可
- 时序图关注调用关系，不关注异常处理和边界情况
- 文字说明和图表要互相关联（如"见类图中的 X→Y 关系"），但不重复——图里有的细节文字不要再写一遍
- 产生交互图时，确保参与者的命名一致——类图里的类名和时序图里的 participant 要对得上
- 全文称呼一致与首现落锚：同一实体换称呼时（类名↔属性名↔中文↔代词；跨图、跨表、图文之间），换名处带一次桥——括号注原名或链接，如 `action_decoder (CategorySpecificMLP)`。任何名字在段落/图/表首次出现处就地可懂：就地一句定义或链接到定义处，不假设读者记得另一张图的 label（"图里画过了"不算数）。写完抽名词扫一遍：每个名词在前文找得到落点或桥
- 每条解释必须带前后左右的对照：上游来源（输入/数据从哪来）、下游去向（结果交给谁）、与相邻编号或流程图哪段对应——只有自身动作、不带衔接的孤立句，读者无法把它安放进系统，等于没解释
- 禁止纯术语堆叠：连续罗列名词而不讲各自角色，是清单不是解释——每个术语出现时要么就地半句说清它在干什么，要么挂链接到展开处；解释的合格线是读者能复述"这件事怎么发生的"，不是"名词都出现过"。典型病灶是"名词（括号塞一句限定）；名词（括号塞一句限定）；……"的分号长链——每个括号都在提示该成员需要独立展开，此时拆成引导句＋编号子条目（先讲共性/因果，子条目各自讲 key、动作、砍掉了什么）
- 术语词条的解释顺序：背景先行（这个现象为什么存在，给带具体数字的画面，如"70 个槽位、当前只有 20 条是真的"）→ 动作分步（每步带代码与形状变化，读者可跟）→ 专名词的每个字有着落（名字各部分指什么）→ 影响与因果。首句禁止术语循环——用被解释词的同族词互相解释（"挑出有效行、结果填回"去解释"散回"），读者原地打转
- 小节标题 = 主题名，不加任何后缀（自设问句、花边角度一律不要），两宗罪：一是把主题偏转成读者没问的问题；二是后缀里的指代往往只有读完正文才能解开——点"NPU 初始化序列"的读者还不知道有 `.npu()`/`.half()` 两个调用，"（为何顺序不能乱）"于他是谜语，正如点"美国"的人不知道"（为什么不叫古巴）"里的古巴是什么。标题必须读者此刻就能完整理解；why 写正文
- 链接必须有信息增量才值得跳：落点内容与链接处同层级重复（速记链速记）等于骗点击；没有详细版就先写详细版，或干脆不挂链接。增量还要对层：读者点"EEF 向量化"是来看改动的是/为什么/怎么做，落点若复述术语表已有的概念解释（想看是什么的人会直接跳术语表），是层次错配——改动小节只写改动，概念留链接
- 结构信息图优先承载：零件/装配关系用局部类图（组合菱形+维度挂关系标注），带循环回环或 shape 流转的流程用 flowchart（回环箭头+每站标 shape）；文字只留图放不下的 why。数据流图的外部输入节点必须标注来源与参与方式（"每轮同一份"/"初值·仅第 1 轮"/旁路虚线），不能光秃秃一根线怼进主流程。每张正文图配图号与图名（`**图 N.M.K：名称**`，放代码块下方；N＝部分号、M＝章号、K＝章内序号，如"图 1.2.1"＝第一部分第 2 章第 1 图）——图号是跨章引用的锚，中途插图只重排该章内的 K；不被引用的插图（如术语表词条内的说明图）不编号
- 复杂流程图的解释用编号引用式承载：节点标数字、变换边标字母，编号格式圆括号 `(1)`/`(A)`；外部输入的虚线节点与边同样入编，每条边独占一个字母（汇合语义写进图下解释）。图下按编号逐条解释涵盖内容，解释按数据流顺序排列（节点与变换交错：1→A→2→B→…），不按编号类型分组；外部输入条目垫最后并逐条标注。图上是浓缩标签、图下是完整说明。图内元素编号与"图名不编号"互不冲突；编号在图结构定稿后再加，避免中途插节点重排
- 性能/精度数字分口径：文档门面（Story、摘要、汇总表）用最终发布口径并注明来源（如上库 README）；开发期实测是过程记录，标注出处并与发布口径分开列，两批数字不混写
- 写适配改动小节前读当前代码取证，三条铁律：① 文中断言以当前代码为准，不凭 commit message（message 说"gather 替换"而 diff 里是 chunk+cat，以 diff 为准）；② "曾试过 X"是中间态、"最终 X"才是终态，别把某次尝试当现状（参数被后来清洗删掉、行为回到无条件）；③ 小节结构写全"是什么 / 为什么 / 怎么做"，能带 shape、公式、新旧代码并排对照更好——先给直觉画面（如"切块称重"）再落符号
- 清单式章节（功能点分解、来源对照表）的每个条目，凡有对号的详细小节，条目名就挂链接指过去（"做了什么"的一句话清单 ↔ "为什么/怎么做"的展开小节，读者点得进去）；多项同属一类时可归类括注（`静态 shape 化三项（a / b / c）`）再逐条链接；条目内首现的术语同样要挂链或就地括注，不因"后文会讲"而裸放
- 代码实体引用挂路径链接，格式 `[路径:行号](/工作区根相对路径#行号)`——显示文本用仓库惯用口径（样例外层文件裸名如 `om_runtime.py:75`、内层仓相对如 `model/module/decoder.py:137`），目标以 `/` 开头（VSCode markdown 预览按工作区根解析，Ctrl+click 直达）并以 `#行号` 锚定定义行（行号取 class/def 语句所在行，落盘后 grep 验证路径存在且行号在文件范围内）。挂载点：逐类速查每条挂类定义行、实现思路小节首现代码实体处。已知代价：行号随代码改动漂移（跳到附近、文件与类名在文本里兜底）；文档拷出仓库后链接失效属安静失败（404/提示通知），不损害渲染
- 长条目列表（图下逐条解释、逐类速查这类每条两行以上的清单）条目之间用空行隔开（markdown 松散列表）——紧凑列表渲染后行距压死，长条目挤成一片；单行短条目的清单不受此限
- classDiagram 不支持 UML `«»` 构型记号：构型注解写成类体内一行 `<<module>>`；静态方法标记用后缀 `$`（`-method()$`），不是前缀；成员行要挂简短说明时借用返回类型槽（`-method() eager`）。类框加编号用类名别名：`class C1["(1) DiffusionPlanner"]`——框标题显示"(1) 类名"、编号融入标题行，关系行以内部 ID 引用（`C1 --> C2`）；需 mermaid 10.5+。成员行内的维数/符号用中文或 ASCII（`7到192`、`3块`），箭头等 Unicode 符号在成员解析里会报错
