# 适配后上库清理（post-port-cleanup）

## 问题本质

适配期 = 高速实验期。判死实验的代码、门控 env、调试 print、写给自己看的注释、一次性脚本层层堆叠——开发者自己看得懂，因为记得上下文。

上库 = 面向陌生读者（队友 / 上游 reviewer / 公开）。他们没有实验战报，看得懂生产代码，看不懂实验残留。

清理 = 把考古层从产品层剥离，**同时不丢知识**（判死结论、平台坑位、重启路径）。

手动做这件事麻烦的根源：清理面分散（代码/注释/脚本/env 各一处）、判断要靠回忆（这个 env 还有没有人用？这段注释删了丢不丢信息？）、验证容易漏（删完编译不过/有残留引用）。本 skill 把它们变成固定清单。

## 流程六步

### ① 定基线："什么是我们的改动"

- fork 结构：`git merge-base <上游/main> <工作分支>`
- 多仓/子模块：每个仓分别定基线，各自出 patch
- ⚠ **别按"第一个文档 commit"或记忆中的日期定基线**——文档目录的引入常晚于代码动手，按它选会把更早的适配 commit 漏在 diff 外。按**作者分界**验证：
  `git log --format='%h %ad %an | %s' --reverse | head -10`，基线取最后一个非我方 commit
- 量级自查：`git diff --shortstat <base>..<HEAD>` 应与"我们做了多少事"的直觉一致；明显偏小 → 基线选晚了，回去重查

### ② 拉全量 diff

`git diff <base>..<HEAD>` 落文件。**不是逐行读**——几万行逐行读不现实也没必要，按③-⑤的审计面对 `+` 行跑 grep。

### ③ 五类审计

| 类 | 判据 | 处置 |
|---|---|---|
| 判死实验代码 | 有实验结论留档（战报/commit message 记了死因）；通常 env 门控缺省关 | **删** + 文档记录原实现（见"知识保真"） |
| 活功能 | 生产路径在用 | 留 |
| 通用 API | 当前无调用者但属能力储备（平台接线件等） | 留（pub/extern 接口不碍编译），注释必须洗 |
| 一次性脚本 | 产物已清 / 已执行 / 实验专用 | **删**；活资产（cron 在用、生产脚本源档）留 |
| 注释 / print | 见④ | 洗或随代码删 |

删实验代码前先确认无活引用：删掉的标识符（函数/env 名/Const 名）全仓 grep。

### ④ 注释清洗

**判据一句话：这段注释删掉后，陌生读者还能正确使用、维护这段代码吗？**

- 能 → 过程残留，删。典型：实验叙事、内部代号、日期、"抢救/临时/workaround"字眼、内部规模数字（几路几档）、部署拓扑细节（哪台机器哪个 supervisor 配了什么值）
- 不能 → 技术实质，留。典型：API 行为约定、平台错误码与怪现象记录、坑位判据（"X 必须先 Y 否则被拒"）、已知限制

洗的目标状态：注释描述**代码是什么、为什么这样写**，不描述**怎么走到这里的**。

### ⑤ 敏感面扫描（对 diff 的 + 行跑 grep，命中逐条人工判）

```
env 门控盘点    env::var( / getenv( / envi(          → 列全部变量名，逐个判：生产接口 or 实验残留
调试输出        println!( / eprintln!( / print_dbg(  → 注册期一次性诊断 vs 常驻日志，前者随实验删
硬编码路径      /home/ /data/ /tmp/ C:\ D:\ ~/       → 上库代码不应含内网绝对路径
内网标识        192.168. 10.0. 主机名 root@           → 同上
日期与代号      20\d\d-\d\d-\d\d 、内部实验代号        → 注释里的实验时间戳/黑话
口语标记        实验|判死|抢救|临时|顺手|hack|FIXME     → 过程残留的高发词
```

### ⑥ 验证与提交

- **grep 清零**：删除项的标识符全仓无残留
- **编译检查**：在能构建的环境跑 check（本地没有工具链就走构建机/容器）
- **生产等价性**：若删的是 env 门控缺省关的代码，论证行为等价 → 运行中的二进制不必强制重编译，下个部署窗口自然对齐（记入 handoff，别留隐性分叉）
- **两步提交**（子模块结构缺一不可）：先子仓 commit + push，再外层 bump gitlink + commit
- commit message 写清：删了什么、原实现记录在哪

## 知识保真：删代码不删知识

判死实验删除前，在**本地工作档案**（如 syx_docs 这类不随上库 patch 分发的文档区——若项目文档与上库仓是分离的，档案可以含内部细节；若文档随仓分发，则档案本身也要过一遍敏感面扫描）写**原实现快照**，模板：

```
门控条件（env 名 + 前置依赖 + 支持路径的限制）
关键步骤（数据布局、命名约定、平台 API 调用顺序）
踩过的坑（错误码、被拒的调用方式、正确姿势）
重启判据（什么条件下这条路线值得重开——通常就是当初判死的反命题）
```

一次性探针/脚本删除同理：逐个记录用途与结论（一张表即可），恢复方法
（`git checkout <删除commit>^ -- <path>`）写明。

git 历史有完整实现，快照只写"恢复时最先要知道的"，并链接 commit hash。

## 边界

- fork 项目只清自己引入的行（`git diff <base>` 的 `+` 行）——上游原有风格问题不动，否则 diff 膨胀、reviewer 困惑（与 code-gatekeep 的边界规则同源）
- lint/门禁规则自查是另一件事，走 code-gatekeep skill
- 清理不重写 git 历史：实验代码留在中间 commit 里就是留档，HEAD 干净即为干净
